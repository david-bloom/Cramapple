## H0 — SubjectPackage v1

The SubjectPackage is a declarative desired-state input. It provides:

- explicit operation: `create-subject` or `create-exam-pack-version`;
- stable subject key and explicit existing-subject key for annual revisions;
- exam identity, semantic pack version, official exam date, and canonical academic year (`YYYY-YY`);
- versioned source records and rights state;
- versioned, hierarchical taxonomy nodes supporting units, topics, objectives, practices, and skills;
- section structure and weights, archetypes, modalities, platform capabilities, and inventory targets;
- verifier profile requirements, gold-set/calibration requirements, and reviewer capability policy;
- the complete set of required release-gate categories;
- fact-pack, authoring-prompt, generator, and generation-time provenance; and
- explicit preservation/retirement/remapping intent for the prior pack.

Cross-record semantic checks belong in the future compiler, not JSON Schema. The compiler must additionally prove that node, archetype, source, and prior-pack references resolve; section score weights sum to 1; each weight minimum is no greater than its maximum; and official exam date maps to the declared academic year.

## H1 — Versioned ItemPackage v1

An ItemPackage carries one proposed canonical content version. It pins the exam pack, taxonomy scheme/version/node references, and archetype version. Stimuli are ordered and structured; parts/subparts are ordered and carry response modalities, points, and rubric criteria. Criteria can declare data-only deterministic checks from a closed registry. Assets require references and accessible representations.

The package deliberately excludes reviewer identities, lifecycle state, approval booleans, environment grants, migration SQL, and executable verifier code. Those are authoritative records produced by other systems. `legacy_projection.frq_form` is explicitly a derived compatibility projection and cannot become identity.

The future compiler must enforce semantic invariants not expressible cleanly in the portable schema:

1. sum of top-level and nested part points equals the archetype total;
2. criterion points reconcile to their containing part;
3. every stimulus/taxonomy/archetype/source reference resolves to the exact pinned version;
4. every declared modality passes capability preflight;
5. content SHA-256 is recomputed from canonical JSON rather than trusted from input;
6. no duplicate ordinals or keys exist within their scope; and
7. schema-to-database compilation is deterministic and idempotent.

## Manifest replacement design

### Canonical relation

Replace the misleading `exam_pack_manifests.artifact_version_ids` array with an immutable child relation named `exam_pack_manifest_content_versions`:

| Field | Contract |
|---|---|
| `manifest_id` | Required FK to immutable manifest; part of primary key |
| `ordinal` | Positive integer; unique per manifest; deterministic ordering |
| `content_item_version_id` | Required FK to canonical `content_item_versions.id`; unique per manifest |
| `content_key_snapshot` | Required immutable audit snapshot; must match the owning item at write time |
| `content_sha256` | Required 64-character lowercase hex; recomputed from canonical payload |
| `created_at` / `created_by` | Audit metadata; no update path |

The manifest is resolvable only when every relation row points to a version belonging to the manifest's exact exam-pack version and no content key appears twice. The relation is append-only once a publication event references the manifest. Manifest SHA-256 is computed over canonical ordered relation rows plus the other exact evidence/version references.

### Compatibility period

- P0 continues writing the exact `content_item_versions.id` into legacy `artifact_version_ids` as a temporary carrier.
- The additive migration backfills the relation only where each legacy UUID resolves unambiguously to `content_item_versions.id` and records unresolved rows as blocking findings.
- During dual-write, the transaction computes both representations server-side and rejects divergence.
- Readers switch to the relation behind a compatibility view; legacy fallback is permitted only for verified pre-cutover manifests.
- The column is renamed/deleted only in a later approved migration after zero legacy readers and full parity evidence. Historical manifests are never rewritten destructively.

## Typed validation registry

Avoid a PostgreSQL enum: categories evolve, while historical suite versions must remain interpretable. Use immutable registry records and versioned suite definitions.

### `validation_suite_types`

| Field | Contract |
|---|---|
| `suite_type_key` | Stable key; initial values below |
| `display_name` | Human-readable label |
| `gate_category` | `source`, `rights`, `content_clearance`, `grading_calibration`, `security_privacy`, or `release_approval` |
| `target_kinds` | Closed set such as content version, exam-pack version, manifest, deployment |
| `waiver_policy` | `never` except content-clearance types may be `product-owner-exception` |
| `active_from` / `retired_at` | Lifecycle bounds; retirement never changes old evidence meaning |

Initial stable keys: `schema`, `content-correctness`, `answer-rubric-consistency`, `grading`, `calibration`, `regression`, `security`, `privacy`, and `security-privacy`.

### `validation_suite_versions`

Each immutable suite version references a type key and contains input contract version, runner kind, deterministic configuration or reviewed plugin identifier, expected target kind, content hash, and supersession link. Arbitrary code is not stored or executed from subject/item config.

### `validation_runs`

Runs reference the exact suite version and exact target identifiers, with start/completion times, environment, runner build/configuration, outcome, evidence URI/hash, and invalidation/supersession state. Eligibility requires at least one current passed run for every required non-waived category, exact target coverage, and no later invalidation.

## Content-clearance exception contract

`content_clearance_exceptions` is immutable and append-only. It does not change review evidence; it is an additional authoritative record evaluated by the content-clearance resolver.

Required fields:

| Field | Contract |
|---|---|
| `exception_id` | Immutable UUID |
| `exception_type` | Stable key, initially `content-clearance` only |
| `scope_type` / `scope_id` | Exact content version, manifest, or exam-pack version; broad subject-wide scope is prohibited |
| `approved_by` | Product Owner identity resolved from authoritative role records |
| `approved_at` | Server timestamp |
| `rationale` | Non-empty decision rationale |
| `evidence_record_ids` | Non-empty immutable evidence references |
| `effective_at` / `expires_at` | Bounded interval; expiry required and after effective time |
| `supersedes_exception_id` | Optional link for correction/replacement |
| `revoked_by_event_id` | Optional append-only revocation event reference |
| `created_by` | Actor that recorded the already-authorized exception |

Rules:

- Only the Product Owner may approve; service-role execution alone is insufficient.
- Scope and gate category are server-validated, not client-asserted.
- An active exception may satisfy only `content_clearance`.
- Rights, source, grading/calibration, security/privacy, and release approval remain non-waivable.
- Revocation, expiry, source withdrawal, or target-version mismatch fails closed.
- Corrections supersede; no update/delete grant exists.

## Migration plan

### M0 — Ratification and preflight

TASK-0009 ratifies canonical identity, multi-scheme taxonomy, manifest relation, registry, and exception concepts. Inventory all legacy manifest UUIDs and all suite-type strings; classify every unresolved value. Capture row counts, hashes, FK orphans, grants, RLS, dependent functions/views, and rollback checkpoint. Stop if any mapping is ambiguous.

### M1 — Additive physical design

After separate approval, add registry tables, immutable suite-version linkage, manifest-content relation, and exception/event tables. Add constraints and indexes without deleting or renaming legacy fields. RLS defaults deny; service functions receive only required privileges. No environment is inferred from the linked CLI project.

### M2 — Backfill and reconciliation

Backfill registry keys from an approved mapping and manifest relation rows from unambiguous canonical content-version IDs. Write a reconciliation report containing counts and hashes. Ambiguous rows become blocking findings, never guessed mappings. AP Chemistry remains scaffold-only and no publication operation is invoked.

### M3 — Server-side dual-write

Update the atomic publication RPC to resolve typed suites and write both manifest representations. It validates equality inside the transaction. Add exception resolution only after its own security and authorization tests. Re-run rollback, exact-version, concurrency, privilege, tamper, expiry, and evidence-target tests.

### M4 — Read cutover

Switch Dev readers to a compatibility view backed by the new relation. Compare normalized semantic snapshots for AP Biology and both AP Statistics packs. Keep the legacy path read-only for verified historical manifests. Production requires a new approval ID and execution packet.

### M5 — Deprecation completion

After an observation window with zero parity failures and no legacy readers, separately approve removal or renaming of the legacy field. Preserve historical evidence and audit hashes.

## Rollback plan

- **Before read cutover:** revert RPC/readers to legacy behavior, stop dual-write, and leave additive records intact for diagnosis. Do not drop evidence.
- **After read cutover but before legacy removal:** switch the compatibility view/readers back to verified legacy rows; keep relation and registry records. Replay parity checks before resuming.
- **After Production publication:** publish/activate the prior immutable manifest through a new rollback publication event. Never mutate the failed manifest or delete its event trail.
- **Schema rollback:** only additive objects with zero authoritative references may be dropped, under a separately reviewed down migration. Otherwise disable new writes and retain them.
- **Content rollback:** retire the newly activated content version and reactivate the exact prior manifest/version through the same atomic gate path; no `latest` inference.

## Security and integrity review requirements

- Fixed or empty function search paths; schema-qualified objects; `security invoker` by default.
- RPC execute privilege limited to `service_role`; user authorization resolved inside the transaction.
- No direct client insert/update/delete on manifests, relation rows, validation evidence, exceptions, or lifecycle events.
- Short transactions and one content-item lock serialize competing version activations.
- Evidence arrays/relations reject duplicates, unknown IDs, stale rights/source records, wrong target versions, invalidated runs, and extraneous rights records.
- Environment and production approval are deployment-authority inputs, not trusted package fields.
- Canonical hashes are server-computed from deterministic JSON/ordered relation rows.

## How the hand-drawn response system can leverage BYOQ

Context, verified in this repo on 2026-10-09: the hand-drawn response path (`TASK-0016` Phase D, `TASK-0020`, `TASK-0025`, `TASK-0038`) captures a student's drawn work through `capture-pairing` into `app.response_attachments`, runs a capture-quality check on the photograph, and routes spatial rubrics to `shadow_review` in `evaluate-attempt` — a hold, not a vision grade. No production path reads the drawn content with a model today. BYOQ now runs a production vision call on student photos every day, with the review loop, cost accounting, security model and benchmark harness around it. The reusable parts, in order of how much they would buy:

1. **"Is this your answer?" — a student-confirmed transcript before grading.** BYOQ's central product finding is that a model's reading plus a student's one-screen confirmation is reliable where a blind read is not. The same shape fits a hand-drawn FRQ response: read the student's written work (values, labels, the line they drew, the axis scale) into a structured transcript, show it beside the photo with every field editable, and grade the confirmed transcript. This turns the Engine 4 problem recorded on 2026-08-18 (OCR and vision reads cannot be trusted as the decider; adversarial re-checks fail; majority vote helps) into a different problem: the student is the decider, the model is a fast first draft, and the grader works on text it can verify deterministically. `captured_work` already proves the model separates handwritten work from printed text. Governance note: BYOQ never grades; the drawn path does. The reuse is code in `_shared/` and a UI pattern, not shared tables or a shared item path (`DECISION-0057`/`DECISION-0068` still hold).
2. **The extraction module as a template for a "drawn-response reader".** `_shared/byoq-extraction.ts` already has the pieces a drawn-response reader needs: a closed strict schema (so nothing can come back that the grader did not ask for), per-call enums built from context (there, topics; here, the rubric's expected elements, axis names or the plot's value set), "visible text only / never invent / blank page abstains" rules that killed the hallucination seen in the benchmark, bounded output, timeouts, and an outcome type that never throws. A `drawn-response-extraction.ts` that reuses `runByoqExtraction`'s call shape and swaps the schema and prompt is a day's work, and it would plug into `capture-pairing` where `runCaptureQualityCheck` already runs after the bind.
3. **The benchmark harness, pointed at drawn work.** `render_fixtures.py` renders published items to pages with free ground truth and planted controls. The drawn path's real gap, recorded in `project_engine4_data_gaps_2026_08_18`, is measured ground truth. The harness can render synthetic hand-drawn-style graphs from the item's own canonical answer (plot the expected points, add a wobble filter, plant wrong points), giving a labelled corpus for the reader in (2) without a single human-labelled photo, and keeping the real-photo corpus (`docs/research/*hand_drawn*`) as the separately-reported cohort, exactly as the BYOQ benchmark treats degraded pages. The same scorer (type/field fidelity, abstention, planted controls, latency, tokens) applies.
4. **Phone-side review through a capability, not an owner key.** `capture_review_get/update/remove_flagged_text` show how a phone that holds only a pairing handle can review and confirm the item it just photographed, for a bounded window after `finish_capture`, with the item fixed by the handle and the owner able to revoke early. `capture-pairing`'s phone leg today only uploads; the same three-op pattern would let a student confirm the transcript of their drawn answer on the phone they used to photograph it, which is where they are standing.
5. **Re-read-then-fill and "unset means still equal to the previous proposal".** Two defects QA found in BYOQ (a mid-call edit overwritten; a re-run unable to refresh an untouched proposal) are generic to any "model proposes, student edits, model may re-run" flow. The fixed semantics in `proposalPatch` plus the fresh-row re-read in `extractForItem` are the ones to copy, with the test cases in `index_test.ts` ("an edit saved while the model is running is kept…", "a re-run refreshes a field that still equals the previous proposal…").
6. **Spend and rate limits that already exist.** Reservation under a fresh request id per call through `app.reserve_model_usage`, completion on every path, a per-owner daily run count from the ledger prefix, and refusal to run without the shared cap: `capture-pairing` reserves for the quality check but has no per-student run cap and no module-level breaker. Lifting `extractionRunsExhausted` and the `byoq_extract:<owner>:…` request-id convention into `_shared/` would give both paths one accounting model.
7. **Same-device capture.** BYOQ's "I'm on my phone — use this device" path, with the canvas-injected-file technique in `scripts/byoq_preview_seed.ts` plus the browser steps in the execution record, is also the cheapest way to QA the drawn path's phone leg without a physical phone (the published app is the test surface; the Lovable preview is behind Lovable's login).
8. **What not to carry over.** BYOQ's answer-material handling (drop printed keys, keep the student's own marks) is right for a question photo and wrong for a response photo, where the student's marks are the evidence. The drawn reader's schema should make the student's work the primary field and keep "printed answer key visible" as a warning for the grader, not a drop rule.

# Checkout browser QA — Sol — 2026-10-06

**Scope:** Public, live, unpaid browser UX only. Marketing site `cramapple.com`; in-app browser (Chromium), desktop 1280 x 720 and mobile viewport 375 x 812. One synthetic `example.invalid` student address. No payment details, payment submission, sign-in-code request, parent-email send, account creation, code review, deployment, commit, or push. This is a fresh observation of the published UI, not a claim about backend state or email delivery.

**References:** `docs/INDEX.md` checkout-user-testing entry; `docs/tasks/TASK-0060-USER-TESTING-CHECKOUT.md` (especially E6, E9, E10 and Still to test); `docs/handoffs/SESSION_CLOSE_2026_10_04_CHECKOUT_USER_TESTING.md`. ## Findings

| ID / severity / evidence | Reproducible trigger and exact UI reference | Student or parent consequence | Shortest-flow improvement |

| B1 / P2 / **Observed** | Open `/checkout` with `subject=biology` (with or without `promo=FRIENDSSPECIAL`). Biology is already checked, yet all ten subject tiles remain expanded. `#co-email` starts at document Y=594 on 1280 x 720 and Y=856 on 375 x 812; the email input is below the initial desktop and mobile view. Sticky `Place order` is disabled. | A student whose subject is already chosen must scroll through the whole picker before seeing the next required action. The disabled sticky action gives no local route to the email field. | For a preselected subject, show a compact selected-subject summary with a clear Change action, followed immediately by the email field. Keep the full picker for `/signup` or an explicit Change action. |
| B2 / P2 / **Observed** | Open `/checkout` with `subject=biology` and `promo=FRIENDSSPECIAL`, before entering email. `#co-promo-input` is filled; the order summary and sticky total show **$39.99**. The enabled-looking `Apply` button responds `Pick your subjects and enter your email first`; the payment area instead says `Apply your promo code, or clear the field, to continue.` After entering a valid synthetic email, the code applies automatically and both totals become **$1.00**, with a **-$38.99** discount line. | The promo link appears to have failed or to cost full price, and the obvious Apply action produces a prerequisite error. This adds a dead-end click before a purchase. | Treat the prefilled code as pending until it can be checked, state that next to the total, and make email the explicit next action. Auto-apply when eligible, as the page already does; do not present Apply as ready before then. |
| B3 / P2 / **Observed** | On the same discounted checkout, choose `Ask a parent to pay`, then `Create payment link`. The modal changes to `Waiting for your parent to pay` with Copy and Share actions. Close the modal and reopen `Ask a parent to pay`: it returns to `Create payment link` with no visible way back to the existing waiting/share state. Reproduced at 375 x 812. | The student can lose the link before sharing it, or create another live unpaid parent session to recover. | Persist the active link and waiting/share state across modal close and reopen; provide an explicit New link action only when needed. |
| B4 / P3 / **Observed** | Open `/checkout` with `subject=biology` and no email or promo. Under `#co-pay`, `Express Checkout` has an empty grey reserved slot; Pay with card and Ask a parent to pay are disabled with `Add your email` beside each. | The wallet slot has no local explanation and can read as failed loading, while the needed email input is above it and initially below the fold. | Put `Add your email to see available wallets` inside the reserved slot, preserving its height. Make the disabled sticky action point visually to the email step. |
| B5 / P3 / **Observed + inference** | Direct `/welcome` shows `Enter the 6-digit code from your email`, but its first required field is `Your email` and the only button is disabled `Continue`. The actual code field is not present in this initial state. | A person coming from an email link has to re-enter their email before entering the code. This may be necessary on a new device; on the checkout return tab it is an avoidable extra action. | Carry the student email in same-tab checkout state when available and show the code field immediately there. ## Step count and boundaries

- **Biology checkout:** subject selection is already done; the visible remaining sequence is enter email -> select wallet/card or parent route -> enter payment details if card -> Place order. The last two payment actions were **not tested**. The checkout UI does not verify email before payment; the published copy says a 6-digit sign-in code arrives afterward. Payment alone must not be assumed to verify that address.
- **Parent path:** enter student email -> Ask a parent to pay -> Create payment link -> Copy/Share -> parent pays externally -> student first sign-in. Only the first three actions and Copy toast/waiting state were tested. One unpaid parent link was created. No live parent URL, code, Stripe session ID, or synthetic address is published here.
- **`/signup`:** choose a subject -> enter email -> choose payment route. The ten-item picker is appropriate while nothing is selected, but B1 applies as soon as a subject comes from a deep link.
- **Untested:** wallet availability and layout shift in signed-in Chrome, Safari or Firefox (this in-app browser exposed no wallet); the copied link bytes and real SMS handoff; a real parent checkout; actual charge, return page, purchase email and Confirm sign up template; code verification, hub redirect/banner, existing-account behavior; invalid promo errors; whether a reused/expired real short code differs from an unknown code. No backend or Lovable source was reviewed in this pass (**Code-reviewed: none**). Conclusions about those paths require their own tests.

**Side effects:** Entering the synthetic address initiated an unpaid checkout session; removing the promo prepared another full-price session. One unpaid parent link was created. Exact session identifiers were not surfaced or retained. No email send or payment action was performed.

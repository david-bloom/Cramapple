## Findings

### P1 — Code-reviewed — Confirmed answer text remains mutable without invalidating confirmation

An authenticated owner may update a draft `app.response_versions` row directly: the owner UPDATE policy permits it and the table grant includes UPDATE (`supabase/migrations/20260731160000_schema_baseline.sql:7204`, `:7909`). The new trigger protects only response-part keys beginning with `_`; it does not protect `response_text` or ordinary part keys (`supabase/migrations/20261009233521_frq_photo_responses_hardening.sql:92-121`). Confirmation stores `_confirmed_at` and the photo digest but no digest of the confirmed response content (`supabase/functions/_shared/response-transcript.ts:203-215`). Submission then checks only that the confirmation exists and its stored photo digest matches the current attachment (`supabase/functions/_shared/response-transcript.ts:90-120`; `supabase/functions/attempt-response/index.ts:1740-1757`).

Adversarial sequence: legitimately confirm answer A; PATCH the owner-writable draft response so `response_text` and/or an ordinary part key contains answer B while leaving the protected `_confirmed_*` keys unchanged; call `submit_response`; the gate accepts the photo digest and `evaluate-attempt` can grade B. That violates DECISION-0110's central guarantee: the graded answer is not necessarily the answer the student confirmed.

Required remediation: make confirmation content-bound and enforce it under the submit transaction. For example, store a server-computed digest of canonical confirmed response content and compare it at submission, or make any owner content change atomically clear confirmation. Do not rely on the Edge Function's preflight read as the integrity boundary.

### P1 — Code-reviewed (interleaving inferred) — Retake-after-confirm has a TOCTOU submission race

The Edge Function reads the current attachment and confirmation before calling the database submit RPC (`supabase/functions/attempt-response/index.ts:1740-1757`, then `:1781-1791`). The actual `app.submit_response` transaction locks the attempt and response version but never re-reads the current attachment or confirmation (`supabase/migrations/20260731160000_schema_baseline.sql:859-893`). `app.bind_response_attachment` uses the same attempt → response lock order and may commit a replacement photo between the Edge preflight read and the submit RPC (`supabase/migrations/20260819120100_bind_response_attachment_writable_guard.sql:91-125`, `:144-168`).

Adversarial interleaving: confirmation is for photo A; submit preflight checks A; a retake binds photo B and commits; the submit RPC then acquires the locks and submits without re-checking that `_confirmed_digest` still matches B. The sequential Development smoke proves the normal retake path, not this concurrency ordering.

Required remediation: move the attachment/digest/confirmation/content checks into the same SQL transaction that locks and submits the attempt and response version, using the established lock order. Add a deterministic concurrency test.

### P2 — Code-reviewed — `photo_required` can be submitted and auto-graded with no photo

The content migration deliberately begins serving hand-drawn items and marks them `photo_required` (`supabase/migrations/20261009230917_frq_photo_responses_content.sql:274-288`). The Lovable screen, however, hides the ordinary Submit button only after the photo panel becomes busy: `photoOwnsSubmit = photoOffered && photoBusy` (Lovable `src/screens/PracticeFrqScreen.jsx:106-110`) and the typed submit remains rendered while that value is false (`:281-290`). With the dark default, non-admin students do not receive the photo panel at all; even with `?photo=on`, they can submit before starting it. The backend transcript gate is intentionally inert when no attachment exists (`supabase/functions/_shared/response-transcript.ts:111-120`). The ordinary Practice flow then invokes its automated grader, bypassing the intended human queue for `photo_required` items.

Required remediation: enforce `response_policy = 'photo_required'` server-side at submission, not only in the UI. Until the photo experience is enabled for a population, keep photo-required items out of that population's selector. In the UI, suppress typed Submit immediately for `photo_required`, not only after photo work has started.

### P2 — Code-reviewed — Redaction can report and cache false success after a lineage-query failure

`redact_attachment` checks the target lookup error but discards the error from the subsequent lineage query (`supabase/functions/attempt-response/index.ts:1266-1278`). A database failure there becomes `rows = []`, produces a successful empty redaction, and records that idempotent result (`:1279-1313`). A retry with the same key cannot repair it. Separately, storage deletion precedes per-row database stamping, so a later stamp failure leaves removed bytes represented as not redacted and is not cleanly retryable (`:1288-1309`).

Required remediation: fail on the lineage query error; make the operation resumable after partial storage/database completion; add failure-injection tests for lineage read, storage remove, and each stamp.

### P3 — Code-reviewed — Tests do not exercise the new submission integrity boundary

The pure helper tests cover digest comparison and the Development smoke covers a sequential retake, but `supabase/functions/attempt-response/index_test.ts` has no handler-level test for the photo confirmation gate, post-confirm direct owner edits, or the retake/submit race. The two P1 defects therefore coexist with a green 587-test suite.

Required remediation: add handler/database integration tests for unconfirmed attachment, post-confirm content mutation, sequential retake, and concurrent retake versus submit.

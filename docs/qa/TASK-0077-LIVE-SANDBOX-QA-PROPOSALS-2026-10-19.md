## Activation: remove the email send from the grant's critical path (design proposal)

Current path: successful SetupIntent → `resolveLearner` → `inviteUserByEmail` → create unconfirmed conversion PI → `trial_activate`. For an unknown learner, an invalid email or mail rate limit throws before activation. The webhook returns 500 and Stripe retries while the payer has already saved a card. Existing users bypass the invitation, so this disproportionately affects new students. Do not solve this by suppressing the error and granting to a payer, or by confirming an email that the student has not verified.

Proposed implementation, intentionally not wired into auth on this branch:

- Extract the trial-specific account resolver from the shared paid-checkout resolver. Find an existing auth user first. Otherwise create an **unconfirmed** auth user with the server-only Admin `createUser` API (`email_confirm: false`), which sends no confirmation email. Preserve the existing name/profile provisioning behavior. Handle a duplicate-email race by looking the user up again, not by creating another identity. Keep verified ownership checks and learner/payer separation.
- Treat permanently invalid addresses as an explicit activation failure: no conversion PI, no access grant, durable reason and a safe correction path. Reuse/refine `activation_refused` cleanup, including parent card detachment; preserve a pre-existing student's own saved card. Return a handled webhook result only after the refusal is durable. Reject syntactically invalid addresses before setup as well. Do not assume syntax validation proves deliverability.
- Atomically enqueue a deduplicated learner welcome/verification job with a successful activation, separate from the payer's trial receipt. A separate worker sends the verification or welcome link with retry/backoff and a visible terminal failure state. For a pre-created unconfirmed user, use the supported generated verification/sign-in link flow; verify that it reaches the existing welcome/password flow before selecting its exact template. Do not assume `inviteUserByEmail` will invite an account already created by `createUser`.
- Mail-rate-limit/provider failures then affect the email job, not Stripe's activation response. Auth/database outages remain real activation failures; retain retryability and a durable diagnostic rather than acknowledging a lost grant. Preserve the original Stripe completion timestamp across retries; if activation is so delayed that the trial/collection window has elapsed, apply the existing delayed-charge protections rather than charging immediately.
- Never log or store a raw auth link in general logs. Keep generated tokens in a protected delivery channel and retain ordinary email verification. Add outbox RLS/privileges and least-privilege worker access in a new migration after reviewing the current auth triggers.

Required implementation tests: new/existing learner; duplicate-user race; invalid address; mail 429 and provider failure; auth 5xx; activation transaction failure; repeated webhook delivery; durable one-per-order welcome; successful verification/welcome/password setup; no parent card mapped onto the student; no duplicate grant or PI. Exercise these with mocks/local fixtures first. Any fresh sandbox activation/email tests require a separately authorized window after the pending activation, not during this QA run.

Reference: [Supabase Admin createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser), [generateLink](https://supabase.com/docs/reference/javascript/auth-admin-generatelink). The changelog was checked; no relevant hosted Admin API breaking change was identified.

## Link “Bank”: it can work off-session, but it is not a literal card (design proposal)

Stripe documents Instant Bank Payments as supporting recurring and off-session payments. With Link enabled, even a `card` allowlist can produce a card-shaped Link payment method funded by a bank: brand `link`, synthetic last4 `0000`, and `card.wallet.type = link`. Do not treat those as a physical card ending in 0000, or infer ACH timing from the word “Bank.” Neither audited journey used this method: A and B both used ordinary Visa cards.

The current product promises “this card.” Recommended narrow policy: disable Link for trial setup and recovery while retaining ordinary card payments. Checkout's documented per-session proposal is `wallet_options: { link: { display: "never" } }` on both trial setup paths. For PI-based recovery, use a dedicated trial payment-method configuration with Link disabled; verify the rendered Payment Element, because excluding the distinct `link` method alone may not suppress Link under `card`. Do not change global payment settings for unrelated pay-now checkouts. Check exact API-version support and a fresh preview before enabling the policy; the main proposal deliberately does not change any configuration.

For existing/newly raced setup sessions, validate the expanded saved method and explicitly handle unsupported Link-funded non-card methods before activation. Do not silently collect a different funding source. Existing orders need an individually reviewed migration/recollection plan, not mass mutation or a second PaymentIntent. The current protected orders must remain untouched.

Alternative if the owner intentionally accepts bank-funded Link: broaden the mandate/UI to “saved payment method,” record the appropriate consent version, correctly label Link, and verify setup → off-session charge → recovery → refund using that actual funding method. General Stripe support is not evidence that this app has passed that journey.

References: [Link integrations](https://docs.stripe.com/payments/link/link-payment-integrations), [Link payment methods](https://docs.stripe.com/payments/link/link-payment-methods), [Instant Bank Payments](https://docs.stripe.com/payments/link/instant-bank-payments), [Checkout create parameters](https://docs.stripe.com/api/checkout/sessions/create).

## Parent Terms link: release gate, not a change made during this run

The session requires Stripe Terms consent but supplies no custom acceptance link. Stripe's default link comes from its public business details. The sandbox account's public business URL is `https://accessible.stripe.com`; that does not by itself prove the exact Terms target. The reported placeholder link must be treated as a release blocker until the actual rendered checkbox link is verified. The account API used here does not expose that specific public Terms setting.

Proposed repair: point the sandbox's public Terms URL at the canonical Cramapple Terms URL, separately configure/verify Production later, and keep `consent_collection.terms_of_service = required`. If an explicit per-session override is preferred, use `custom_text.terms_of_service_acceptance.message` with a Markdown link to a server-owned, validated Cramapple Terms URL, and test that the checkbox's actual link has changed. Do not rely on an adjacent submit message or a database version string as proof of what the payer accepted. Test both new and existing hosted sessions because previously created sessions can retain old content. No config change was performed here.

Reference: [Checkout customization and Terms consent](https://docs.stripe.com/payments/checkout/custom-components?platform=web&payment-ui=embedded-page).

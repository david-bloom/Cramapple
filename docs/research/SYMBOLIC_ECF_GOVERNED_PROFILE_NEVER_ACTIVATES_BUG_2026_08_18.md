# `findStatisticsItem`'s governed-profile argument is silently dropped — Engine 3's only published item gets zero ECF verification — 2026-08-18

**Trigger:** found incidentally while verifying an unrelated merge (TASK-0025
QA-fix PR #84) compiled cleanly. `deno check` on `evaluate-attempt/index.ts`
failed with a real type error at the `symbolic_ecf` routing branch — not
something introduced by that merge; reproduced identically on the commit
immediately before it (`c9a8e55`), so this predates and is unrelated to
TASK-0025.

## Diagnosis

`evaluate-attempt/index.ts` calls:

```ts
const statisticsItem = findStatisticsItem(
  contentItem.content_key as string | null,
  contentVersion.prompt_json,
);
```

— a 2-argument call, passing the item's `prompt_json` so a governed
`verification_profile` authored on the content item itself can be used.
But the **committed** `findStatisticsItem` in
`supabase/functions/_shared/math-verifier.ts` only accepts one argument:

```ts
export function findStatisticsItem(contentKey: string | null | undefined) {
  return contentKey ? STATISTICS_ITEM_KEYS[contentKey] ?? null : null;
}
```

JavaScript doesn't enforce function arity, so this doesn't throw at
runtime — the second argument is silently discarded and the call falls
through to a plain lookup in `STATISTICS_ITEM_KEYS`, a hardcoded 5-item
fixture map (`APSTAT-MOD3-H001-INV`, `-MOD5-H001-INV`, `-MOD6-H001`,
`-MOD7-H001`, `-MOD8-H001`) that was "originally authored for" pre-publication
test items per its own doc comment.

**The intended fix already exists — uncommitted.** A `findStatisticsItem(contentKey,
promptJson?)` implementation with the real governed-profile logic
(`validateVerificationProfile`, `buildStatisticsItemProfileFromGoverned`, a
documented fixture-fallback-on-invalid-profile policy) is sitting in this
session's stash (`stash@{0}` on the now-deleted
`claude/gold-set-answer-assignments-o3ibgi` branch, set aside to merge PR
#84 — recoverable via `git stash list` / `git stash show -p stash@{0} --
supabase/functions/_shared/math-verifier.ts`) along with matching tests in
`math-verifier_test.ts` ("findStatisticsItem prefers a valid governed
prompt_json.verification_profile over the fixture map", etc.). Someone
built this, the caller in `evaluate-attempt/index.ts` was updated to use
it, but the `math-verifier.ts`/`math-verifier_test.ts` side was never
committed — only the caller landed.

**Confirmed live in Production, not just a local/compile-time issue.**
Fetched the actually-deployed `evaluate-attempt` source
(`get_edge_function`, project `pcntajvbdfqhbeewmdry`) and confirmed it
already contains the 2-argument call — this has been live since at least
whenever `evaluate-attempt` was last deployed with this call site, not
something that would only bite on a future deploy.

**Concrete, current impact — checked directly against Production content:**

```sql
select ci.content_key, civ.status, civ.evaluator_strategy,
  (civ.prompt_json ? 'verification_profile') as has_governed_profile
from app.content_item_versions civ
join app.content_items ci on ci.id = civ.content_item_id
where civ.evaluator_strategy = 'python_symbolic_ecf';
```
→ exactly one row: `APSTATS-SFRQ-003`, `published`, `has_governed_profile:
true`.

This is Engine 3's flagship item — per the activity log, "Engine 3 Stage
B: First Real Published Item (APSTATS-SFRQ-003) Routed to Production
Shadow, Full ECF Cascade Verified End-to-End with Structured Input"
(2026-08-14). `APSTATS-SFRQ-003` is **not** one of the 5
`STATISTICS_ITEM_KEYS` fixture keys, so `findStatisticsItem` returns
`null` for it today — every real submission to this item's `symbolic_ecf`
route currently falls into the `statisticsItem`-is-`null` branch
("no symbolic verification profile was available for this item, so the
response is routed for follow-up"), **not** the governed-profile ECF
verification path the 2026-08-14 entry describes as already working. The
`shadow_result.profile_source`/`profile_version` fields are also always
`null` as a result (the fixture-derived `StatisticsItemProfile` shape has
neither field, matching the exact `deno check` error this was found from).

Because `symbolic_ecf` is explicitly shadow-only, non-authoritative
(TASK-0016 addendum: "Engine 3 ships shadow-only for now... cannot be
authoritative today") this does **not** change any student-visible score
today. The real damage is to the shadow pilot's own purpose: whatever
shadow data has been collected from `APSTATS-SFRQ-003` submissions since
this call site was deployed was generated by the "no profile available"
fallback path, not the governed-profile ECF cascade Engine 3's
go/no-authoritative decision is supposed to be based on.

## Fix

**Not applied — flagged, not fixed**, per explicit scope decision this
session (found while verifying an unrelated PR merge; fixing grading-engine
verification logic without dedicated review felt like the wrong call to
make as a drive-by). The fix is very likely just: commit the stashed
`findStatisticsItem`/`validateVerificationProfile`/
`buildStatisticsItemProfileFromGoverned` implementation and its tests from
`stash@{0}` (recover with `git stash show -p stash@{0} -- supabase/functions/_shared/math-verifier.ts supabase/functions/_shared/math-verifier_test.ts`,
review it fresh since it's from an earlier session and hasn't been
re-verified against the current codebase), then redeploy `evaluate-attempt`
to Development and Production and re-verify `APSTATS-SFRQ-003` actually
exercises the governed-profile path (not just that it type-checks).
